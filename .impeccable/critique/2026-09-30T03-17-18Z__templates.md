## Design Specificity Verdict

**Design review**: Clearly authored for FRC scouting under competition pressure, not a generic tool — deliberately-kept red/blue alliance convention, FRC-specific pit questions (driver safety, battery-swap turnaround), Q-number match links, EPA/TBA integration, and the OR-together multi-scout checklist reconciliation are all things nobody invents for a generic form tool. It slips toward "could be any data tool" at exactly one place: when Gemini fails, the app shows a raw upstream JSON error string with zero product voice — the one surface that isn't FRC-specific because it isn't really *designed* at all.

**Deterministic scan**: Static/regex detector returned zero findings across all 8 template files — but the sanity check this time surfaced something new: the detector's static mode has a real coverage gap (a synthetic box-shadow anti-pattern never fired in regex mode, only `overused-font` did), so a clean static result here should be read as "nothing this limited mode can catch," not "no anti-patterns exist." The live, rendered-page pass confirmed that gap matters: it found real issues invisible to static analysis — `low-contrast` on Next Match at two different background pairs (3.8:1 and 4.3:1, both failing the 4.5:1 minimum), `nested-cards` and `line-length` on Next Match, and a large `text-occlusion` count on Pit Scouting that Assessment B itself traced to a detector limitation (see below), not a real defect.

**Convergence — a strong one**: Assessment A independently flagged the AI-failure presentation as the single biggest issue in the whole app (a P0, on product-principle grounds) purely from using the product. Assessment B, working blind to that, separately measured the *exact same surface* failing WCAG contrast — the red error text Next Match shows when Gemini fails is `#dc2626`, measured at 3.8:1 on one background and 4.3:1 on another, both below AA. Two independent methods landing on the same broken surface, one on content/UX grounds and one on a hard color measurement, is unusually strong corroboration that this is the app's real priority.

## Cross-Page Consistency (new this pass — a whole-app critique's actual value-add)

- Video Scouting (the newest feature) mostly fits: same `ps-card`/`ps-panel`/`ps-chip` vocabulary, same match-row pattern as Next Match, same save-pop language as Pit Scouting. It does not structurally stick out.
- But its team picker inverts Pit Scouting's own convention for the identical concept: Pit Scouting *deemphasizes* an already-scouted team (grayed, strikethrough); Video Scouting *emphasizes* an already-reviewed team (gold highlight). Same idea, opposite visual weight, on two nearly-identical team grids.
- "Fresh" is a green success pill on Pick List/Next Match, but a gold chip on Match Planner — for the same status word.
- Pick List's header is centered; Match Planner's structurally identical header card is left-aligned, no functional reason.
- The live Scout page shows the raw event key ("2026test") instead of the friendly name every other page resolves via `eventNameFor()` — confirmed in `main.go`, `ScoutPage` is the one handler that skips this.
- Score-bar colors: Scoring uses the brand gold token; Reliability and Defense use hardcoded hex/Tailwind values that bypass the `--ps-*` custom-property system everything else uses.
- One genuine cross-page win worth naming: the WCAG contrast fix from the last critique (darkening `--ps-muted`) is global, so it quietly improved every page's captions, not just Video Scouting.

## Overall Impression

The app's craft is real and consistent almost everywhere it's actually been designed — the offline-save language, the restrained one-primary-action palette, the FRC-specific vocabulary. The one place that craft visibly drops is precisely the app's own stated reason for existing: when the AI can't produce a verdict, the app does the opposite of what PRODUCT.md's first principle demands, and it does so on a condition (depleted API credits) that is not hypothetical — it's the exact state this build is in right now.

## What's Working

1. **Offline-first save language is consistently surfaced, not just implemented.** Device-first save copy, the green "Saved" pop, the sync queue badge — visible everywhere it matters (Scout, Pit Scouting, Video Scouting), directly delivering on Product Principle 4.
2. **Disciplined, meaning-driven color use app-wide.** One red primary action per screen, alliance red/blue kept authentic but tuned to the brand, muted secondary/ghost buttons — this restraint holds consistently across every page, not just one.
3. **The Video Scouting tag-pill interaction is genuinely clever and verified working end to end** — a real solution to "write once, attribute selectively" that reflects actual thought about how someone reviews match footage.

## Priority Issues

**[P0] AI-failure presentation directly contradicts the product's core trust principle — and it's independently confirmed as a real contrast failure, not just a UX complaint.** When Gemini errors (a real, current operating condition, not a hypothetical), Next Match, Pick List, and Match Planner all dump the raw upstream JSON error text verbatim, repeated once per team card, while score bars still show a confident "0/10" instead of the "Low data" suppression used elsewhere for genuine uncertainty — and Next Match's "We're on ___" label goes blank as collateral damage. Measured independently: that red error text (`#dc2626`) fails WCAG AA at 3.8:1 and 4.3:1 against the app's two backgrounds (need 4.5:1).
Why it matters: PRODUCT.md's principle #1 is "an AI verdict must show its own uncertainty... rather than sound confident regardless of what it's actually based on" — this is the one scenario where the app does the opposite, triggered by something as mundane as running out of API credits mid-event.
Fix: catch the AI-call failure once per request/section (not once per card), render a single calm, human error message reusing the existing "Low data" suppressed-verdict treatment instead of raw JSON and confident-looking 0/10 bars, decouple schedule-derived fields like "We're on" from the AI response so they still render when analysis fails, and fix the error text's color to meet contrast regardless. Pages: Next Match, Pick List, Match Planner.

**[P1] The app's own uncertainty-disclosure machinery lives in hover-only tooltips, invisible on the primary device.** EPA meaning, the low-data threshold, what a verdict badge represents, Statbotics-forecast framing — all in `title="..."` attributes, which don't fire on tap.
Why it matters: PRODUCT.md says usage is mostly on phones, and this is exactly the disclosure Principle 1 depends on — present in the code, functionally invisible to most real users.
Fix: move the critical explanations into visible inline text or a tap-to-reveal affordance; reserve `title` for genuinely secondary context. Pages: Pick List, Next Match, Match Planner.

**[P1] The highest-stakes page in the app shows the raw event key instead of the event name.** Every other page renders "Test Event 2026"; the Scout page renders "2026test" because its handler is the one place that skips `eventNameFor()`.
Why it matters: this is the page used live, under time pressure, mid-match — the one moment a scout is most likely to double-check "am I on the right event," and the one place that fails to answer in plain language.
Fix: pass the resolved event name through to `ScoutPage` the same way every other handler does. Page: Scout.

**[P1] Three-robot mode on a phone forces multiple screens of scrolling, and the voice controls scroll away with everything else.** Verified at 375px: reaching the third team's notes requires scrolling past two full-height textareas, taking the voice toggle — the feature meant to make manual scrolling unnecessary — out of view with it.
Why it matters: this is the moment of maximum time pressure (mid-match, three robots, one scout) on the actual device most scouts use, and the fallback when voice isn't working is heavy manual scrolling.
Fix: a sticky mini voice-bar/team-switcher on scroll, or lighter per-team note height with expand-on-focus for the 3-robot + narrow-viewport case. Page: Scout (mobile, 3-robot mode).

**[P2] "Fresh"/"Cached" badges disagree on color for the identical concept.** Green pill on Pick List/Next Match; gold chip on Match Planner.
Why it matters: this is exactly the kind of signal a strategy-team member scans quickly between matches — inconsistent coding for the same status undermines fast recognition when speed matters most.
Fix: standardize on one treatment (the existing `ps-chip`/`ps-chip-gold` pattern), reserving green for genuinely positive outcomes elsewhere. Pages: Pick List, Next Match vs. Match Planner.

**[P2] "Already has data" is visually inverted between Pit Scouting's and Video Scouting's near-identical team pickers.** Pit Scouting grays out a scouted team; Video Scouting gold-highlights a reviewed one.
Why it matters: this is the one shared component type between an established feature and the newest one, and they disagree on what "done" should look like.
Fix: pick one semantic (recommend keeping "done" visually receding, consistent with Pit Scouting) and apply it to both. Pages: Pit Scouting, Video Scouting.

## Persona Red Flags

**Casey (Mobile)** — the most relevant persona for a phone-first tool: 3-robot mode's scroll-away voice controls (P1 above); the Scout page literally says "2026test" instead of "Test Event 2026" on the one screen a competition-day scout glances at to confirm they're on the right event; every tooltip-only explanation on Pick List/Next Match/Match Planner is dead weight on a touchscreen.

**Sam (Accessibility)**: the same tooltip issue doubly applies — `title` is an unreliable channel even for assistive tech and zero-benefit for a touch-only sighted user, who is the actual majority case. Worth noting as a genuine positive: the global `--ps-muted` contrast fix from the last critique benefits every page's captions, not just Video Scouting.

**Riley (Stress-Tester)**: triggering "Run Analysis" under a realistic mid-event condition (depleted API credits) doesn't fail once — it floods Pick List with a dozen copies of the identical stack trace and silently corrupts an unrelated field ("We're on ___" on Next Match) as a side effect. A stress-tester hitting this mid-event would reasonably conclude the whole analysis system is broken, not just rate-limited.

## Minor Observations

- The Scout page's "(N pts)" label next to a team name means "prior scouting submissions," but reads like a score in an app full of real match points and EPA — worth a less overloaded word ("2 logged").
- Reliability/Defense score-bar colors are hardcoded rather than pulled from the `--ps-*` token system.
- Pit Scouting's `text-occlusion` detector findings (the large majority of that page's flagged count) are a confirmed false positive: the question list sits inside a collapsed `<details>`, and the detector appears to walk DOM text without excluding closed-disclosure content — not a real defect.
- The detector's static/regex mode has a real coverage gap (confirmed via sanity check: a synthetic box-shadow anti-pattern never fired), so a clean static scan should not be read as "no issues" — only the live browser pass catches computed-style problems like contrast.
- Seed pit-scouting notes are numbered answers ("1. All-around... 2. Offense...") that only make sense next to the expanded question list — worth checking whether real scouts write notes the same way.
- The remembered scouter name (`localStorage`, per device) is a sensible convenience for a solo scout's own phone, but will silently mis-attribute notes on a shared team tablet passed between scouts.
- `nested-cards` and `line-length` findings recur on Next Match and the Video Scouting review page — same low-priority pattern already noted in the last critique, not new.

## Questions to Consider

1. Gemini billing running out mid-competition is exactly the state this build is in right now — should the AI-failure path get the same design investment as the offline-save path did, given the product's own principle is specifically about the AI's presentation of uncertainty?
2. If two scouts share one tablet back-to-back, does the remembered-scouter-name convenience quietly become a data-integrity problem exactly where Principle 3 depends on knowing who said what?
3. Could a thumb brushing a checklist tag while scrolling silently flip a reliability signal with no visible trace, given the checklist buttons sit directly above a large scrolling textarea?
